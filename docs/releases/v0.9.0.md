# Playlist AI v0.9.0 — Choose your recommendation engine

Playlist AI 0.9.0 gives you control over how recommendations are made: prioritize
archived AcousticBrainz analysis, prioritize local CLAP preview comparisons, or
use the original Deej-AI embedding engine alone. It also reduces repeated
similarity searches, fixes Windows metadata installation and native-analysis
packaging, and records the results of all 40 example prompts in all three modes.

These notes cover changes since the v0.8.0 tag and the additional functionality
available to users upgrading from the last public release, v0.7.0. The existing
v0.8.0 release remains an unpublished draft.

**Release status, checked September 10, 2026:** v0.9.0 is still a draft.
Cross-platform CI and release packaging passed, and all 17 expected assets are
attached. Publication remains pending the packaged-updater checklist described
below. Updating these notes does not publish the release or replace its binaries.

## 1. Three recommendation modes in Settings

Open **Settings → Recommendations**. The preference is saved locally and applies
to new generations without restarting.

| Mode | What leads recommendation ranking | Main boundary |
| --- | --- | --- |
| **AcousticBrainz first** — default | Supported archived recording analysis leads overlapping characteristics; CLAP fills gaps. | Many recordings and requested characteristics lack usable archive evidence. |
| **CLAP first** | Local preview-to-description comparisons lead where available; AcousticBrainz fills gaps. | A preview covers only part of a recording and similarity is not a musical-fit guarantee. |
| **Deej-AI only** | The original audio and playlist-co-occurrence embedding walk. | Requires a resolved catalog reference and cannot verify genre, mood or other musical characteristics. |

The recommendation mode is separate from the parser. You can still use a local
LLM to interpret an artist or track request while selecting Deej-AI-only for
generation. Without an LLM, catalog-only generation continues to require a seed
artist or track.

### Source priority is not a constraint override

Both analysis sources can still participate in eligibility checks in the
enhanced modes. Prioritizing a source does not permit ignoring artist exclusions,
recording deduplication, strict no-vocals checks or required-track conflicts.
Unknown evidence is not proof of musical fit, and disagreements remain visible.

For readers inspecting scores, AcousticBrainz-first uses archive weight **0.55**
and the default semantic/CLAP weight **0.35**. Decisive archive comparisons
suppress overlapping preview contributions for ranking only. CLAP-first uses
archive weight **0.15** and lets available preview comparisons lead overlapping
clauses. Raw evidence remains intact for eligibility, explanations and replay.
Missing clauses retain fixed denominators rather than increasing other scores.

These are explicit source-preference policies, not calibrated probabilities or
weights demonstrated to be optimal by a listening benchmark.

### What engine-only intentionally leaves out

Deej-AI-only does not use provider enrichment, semantic retrieval, CLAP,
AcousticBrainz, taste-profile ranking or the enhanced MMR selector. It keeps
supported artist exclusions, reference-artist exclusions, recording deduplication
and explicit artist spacing.

It explains unsupported requirements, including strict musical verification,
artist-only/album constraints, date limits and the newer resolved-destination
contract. Its original waypoint journey remains available. Descriptive requests
under the best-available policy may return partial, unverified suggestions if
usable seeds exist; missing seeds produce a request for a catalog reference.

The artist-diversity slider is disabled in this mode. Discovery and transition
controls retain the original walk's seeded behavior, rather than the enhanced
engine's exploration and diversity rules.

## 2. Description, discovery and playlist-flow improvements

The release carries forward the grounded-intent work prepared for v0.8.0 and
adds fixes exercised by the forty-prompt suite:

- Explicit artist/track references, inferred retrieval anchors, required output
  tracks, essential musical criteria, exclusions and soft preferences remain
  distinct. A category such as “electronic music” should not become an automatic
  artist lookup for “Electronic.”
- Reference-based requests favor catalog embedding retrieval; genre requests can
  draw on local music metadata and bounded provider discovery. Artist/title
  matching establishes identity, not musical category.
- Grammar-constrained local parsing bounds whitespace, strings and numeric
  expansion. Count handling preserves forms such as “10-song” and “10 jazz songs”
  without consuming the genre words. Negative descriptions preserve their source
  evidence while scoring the negated concept separately.
- Metadata can recover some source-grounded category omissions without introducing
  a fixed list of allowed genres. Parser issues remain observable; a repaired
  interpretation is not reported as a flawless LLM parse.
- Iterative discovery collects an overcomplete eligible pool before final ranking,
  artist-balanced selection and sequencing. It continues searching within its
  budgets when selection cannot fill the requested count.
- Multiple named references can guide a soft embedding transition without making
  every seed mandatory. Genre stages and explicit required tracks retain distinct
  roles. Known destination failures are listed below.
- Preview lookup tries a plain artist/title search before one alternate fielded
  search on empty results, while retaining artist/title/version corroboration.

This is not a guarantee that every genre, adjective or journey will be understood
or verified. Unsupported and insufficiently supported requests still need an
honest partial result, refinement or clarification.

### Generation starts when you ask

Typing or selecting an example only edits the description. **Generate** starts
processing and disables the button while busy. The playlist screen reuses the
returned result instead of immediately building it a second time.

**Regenerate** returns through the Generate flow with the original description
and starts fresh. Cancellation and stale-response protection keep older requests
from replacing newer UI state. Saved history includes lossless string RNG seeds
and available intent, discovery, profile and evidence snapshots.

## 3. Local music knowledge, composer credits and acoustic evidence

### Optional Discogs dataset

Setup can download the compact, catalog-matched Discogs SQLite bundle separately
from the application. Compatible local metadata is consulted before online genre
discovery, reducing network requests.

The measured September composer-aware bundle is **92.6 MB compressed** and
**312.8 MB installed**, matching **586,161 of 956,917 catalog tracks**—about 61%.
This is metadata coverage, not verified recording-level musical-fit coverage.
Downloads check compatibility, sizes and hashes before activation.

Explicit **Composed By** and **Music By** credits preserve their source, track
positions, name variations and uncertainty about release-wide scope. Composer
identity is not guessed from the performing artist or generic writing credits.

The developer-only Go `metadatapack` tool imports checksum-verified dumps with
bounded multi-core workers and builds the compressed runtime index. Desktop
users download the compact bundle, not the multi-gigabyte source dumps.
The measured composer-aware import took **18m 29.65s** with eight workers, followed
by **1m 17.67s** for runtime packing; these are dataset-build measurements.

### What AcousticBrainz contributes

Confidently resolved recording MBIDs can receive cached tempo, key, duration,
loudness and supported genre/mood/vocal classifier evidence. Bulk lookups are
bounded, optional and cancelable. Local Discogs candidates without a resolved
recording MBID can remain uncovered; the app does not perform an extra identity
search for every local candidate merely to obtain optional acoustic features.

Comparisons preserve model versions, provenance, missingness and disagreement.
Strong opposing or conflicting predictions can screen essential requirements;
positive predictions do not bypass other eligibility checks. Scores are not
treated as calibrated probabilities of satisfying the listener's request.

BPM and key are descriptive measurements, not newly enforced prose-derived tempo
limits. “Microdetail,” “sparkle” and many compound or unmapped concepts remain
unknown to the archive comparison layer. Available CLAP comparisons can provide
another view, but neither source guarantees whole-recording properties.
Downloaded AcousticBrainz dump archives are **not yet integrated into a local
runtime index**.

## 4. Fewer provider calls and clearer cache controls

| Source | Freshness and reuse | Outage behavior |
| --- | --- | --- |
| MusicBrainz | Reuse successful responses younger than seven days, including empty searches. | Valid older responses may be used without resetting their age. |
| AcousticBrainz | Seven-day cache for projected recording features and confirmed missing recordings. | Older features can remain usable; outages are not recorded as missing music. |
| Discogs API | Separate freshness window of less than six hours. | Expired content is not served. |
| Deezer metadata | Existing 24-hour cache policy. | Existing stale-data fallback remains. |

Larger provider pages, buffered iteration, canonical query keys and shared
in-flight requests reduce repeated network work. Errors and invalid responses
are not converted into cached empty successes.

Optional token-configured Discogs fallback is limited to **25 requests/minute**.
It is not a replacement for every MusicBrainz capability: canonical recording
identity, work dates, genre relationships and ISRC evidence can remain unknown.
A healthy empty or ambiguous MusicBrainz result is not simply overridden.

**Settings → Music metadata → Clear metadata cache** stops active generation and
clears provider metadata caches and parsed-intent reuse. Late responses cannot
refill the cleared cache. It keeps playlists, saved evidence, taste data, models,
credentials, the installed dataset and derived audio features. **Clear analysis**
is a separate control.

Discogs credentials are stored locally outside preferences and sent through an
Authorization header, not query URLs or saved playlists. The token file is
protected by local permissions/ACLs, **not an encrypted keychain**.

## 5. Performance improvements, with measured scope

### Exact retrieval within a generation

Profiling attributed **94.2% of sampled CPU time** in the reference-based
iterative path to exact similarity scans. Repeated picks were re-running
unchanged reference queries.

A request-owned cache now stores score-ordered prefixes, reapplies the current
exclusions and expands or falls back to exact search when necessary. An LRU
bounds it to **64 queries and 4,096 matches per query**, approximately 8 MiB of
match records plus keys and temporary allocations. It is not shared across
generations, and no ANN backend was added.

The controlled fixture generated ten tracks from Boards of Canada with seed
`42` over the 956,917-track catalog on Linux/WSL2, Core Ultra 9 285H, Go 1.27.1.
Each row summarizes three samples of three iterations; complete playlists and
scoring evidence were compared for equivalence before timing.

| Retrieval implementation | Median | Observed range | Allocated bytes/op |
| --- | ---: | ---: | ---: |
| Uncached exact search | 1.888 s | 1.711–1.915 s | 32,387,048 |
| Request-local exact cache | 0.325 s | 0.315–0.347 s | 27,100,253 |

That is approximately **5.8× faster**, with **16% fewer allocated bytes** and
**21% fewer allocations** on this fixture. Startup, model parsing, provider
access and CLAP inference are excluded. This does not establish a comparable
whole-app speedup or improved musical quality.

### Other reduced work

- Indexed artist lookup reduced the median Radiohead catalog lookup from
  **76.94 ms to 0.503 ms** on a separate controlled fixture. It adds startup index
  work and more temporary allocations; it is not a complete generation benchmark.
- Checking audio stop/budget flags no longer creates and hashes a full evidence
  snapshot. A synthetic 200-assessment benchmark changed from roughly **180 µs**
  and **156,897 allocated bytes** to a zero-allocation status check. Full
  snapshots remain available for history.
- Four historical non-incremental selection helpers moved into the independent
  test oracle. This removes dead production source, not claimed executable bytes:
  the linker already discarded unused functions.

## 6. Forty prompts, three modes: actual regression results

All **120 cases completed**, with ten tracks requested per case. Passing required
at least five distinct recordings, no more than ten tracks, appropriate references
and interpretation, and at least three artists without adjacent artist repeats.
The explicit single-artist request has an artist-variety exception.

| Mode | At least five tracks | Exactly ten tracks | All assertions passed | Reported outcomes |
| --- | ---: | ---: | ---: | --- |
| AcousticBrainz first | 39/40 | 39/40 | 38/40 | 12 fulfilled, 27 partial, 1 needs clarification |
| CLAP first | 39/40 | 39/40 | 38/40 | 12 fulfilled, 27 partial, 1 needs clarification |
| Deej-AI only | 9/40 | 9/40 | 9/40 | 9 fulfilled, 26 needs clarification, 5 unsupported |

Every nonempty playlist met its artist-variety requirement. There were no
recording-duplicate or adjacent-artist assertion failures. Nevertheless, **no mode
met the five-track minimum for every example**. All three live runs exited
nonzero because their assertion failures were retained.

### Known failures, not hidden by passing reruns

- **Spacious electronic music with “occasional sparkle”:** both enhanced modes
  returned ten tracks, but preserved the phrase under styles rather than the
  expected texture field. This is a classification mismatch, not a lost phrase.
- **David Bowie → Talking Heads:** both enhanced modes returned zero tracks.
  The interpretation additionally made artist names essential journey styles,
  and the chosen Talking Heads destination lacked preview evidence. The result
  was `required_track_audio_conflict`, not silent substitution or claimed success.
- **Engine-only:** 26 requests lacked usable seeds, including the unresolved
  Japanese artist reference `宇多田ヒカル`. Five requests were unsupported:
  three newer destination journeys, strict no-vocals, and artist-only filtering.
  These guarded outcomes do not satisfy the minimum-output target.

### Timing, protocol and uncertainty

| Mode | Median per case | P95, nearest rank | Maximum | Sum of case times |
| --- | ---: | ---: | ---: | ---: |
| AcousticBrainz first | 42.3 s | 195.8 s | 709.8 s | 49.6 min |
| CLAP first | 28.3 s | 70.2 s | 342.4 s | 23.1 min |
| Deej-AI only | 0.584 s | 1.357 s | 1.997 s | 27.0 s |

The strict instrumental/no-vocals request took **11.8 minutes** in the first run
and exhausted its analysis budget. It returned ten tracks with a partial
outcome. The distorted-guitars/mood case took 467.0 s initially and 99.8 s in
CLAP-first.

The host was Linux/WSL2 with 15,781 MiB RAM and an RTX 5060 Laptop GPU reporting
8,151 MiB VRAM. Parsing used the installed Qwen3.5-9B Q4_K_M; CLAP used native
ONNX Runtime 1.26.0 on CPU. All modes used seed `42` and an empty taste profile.

Only AcousticBrainz-first parsed fresh. The other modes reused the same 40 raw
version-8 interpretations before metadata discovery. There were **zero parser
fallbacks in those 40 fresh parses**, not 120 independent parsing observations.
The enhanced replay retained the LLM for replacement-anchor proposals.

Caches were retained; CLAP-first followed the first run, with warmer evidence
caches. Some validation and engine-only work overlapped. Timings exclude
model/catalog initialization. Provider responses and candidate pools were not
frozen. These numbers therefore **do not establish a source-priority speedup**.

Each enhanced run selected 390 tracks, with eligible analyzed-preview evidence
for **270**. Neither had selected-track AcousticBrainz comparison scores, although
candidate snapshots included some available archive records. Only four enhanced
playlists differed in ordered track IDs. This evidence cannot establish which
source priority sounds better.

An earlier development report combined a full run and targeted rechecks to
reach 40/40 observed cases. It remains a historical baseline, **not a replacement
for this later paired three-mode result**. No new held-out listening judgment set,
general musical-fit calibration, exact acoustic-energy matching or quality winner
is claimed. The default LLM was not changed to conceal pipeline failures.

## 7. Windows fixes and native analysis prerequisites

### Metadata installation

Windows SQLite URI construction now handles drive letters and backslashes,
fixing the music-metadata installation failure:

```text
SQL logic error: invalid uri authority: C:%5CUsers...
```

### Built-in CLAP worker

Both Windows amd64 and arm64 packages now enable cgo and include the isolated
native CLAP worker in the desktop executable. This fixes:

```text
this application build has no native CLAP worker
```

The older v0.8.0 Windows draft installers predate this correction. Re-downloading
the model does not fix those executables; users need the newly built app.

The wizard checks build capability before downloading a recommended analysis
bundle and provides skip/upgrade guidance for unsupported builds. Legacy custom
bundles can still supply their own worker. Models and compatible ONNX Runtime
libraries download separately through setup.

**Python is not a desktop runtime requirement.** Core recommendation packages
remain covered by the pure-Go compilation gate. The native audio worker does
require the downloaded native inference library; this is not a claim that every
optional analysis component is statically linked into one dependency-free file.

Windows ONNX Runtime requires Microsoft's Visual C++ runtime. The native worker
does not remove that prerequisite. Windows x64 installer/health tests ran through
WSL interoperability, including a production worker with an empty executable
search path. Windows ARM64 inference on actual hardware, clean Windows runtime
prerequisites and hardened macOS runtime signing remain validation limits.

## 8. Upgrade, compatibility and data handling

- **Upgrading from v0.7.0:** install the matching package manually once v0.9.0 is
  published. Existing v0.7.0 binaries do not acquire an updater retroactively.
- **History:** old intent and playlist records remain readable. Existing saved
  results are not rewritten. Requests without a recommendation mode use the
  current desktop default when rebuilt; requests with a mode retain it.
- **Current settings:** Regenerate starts fresh using the latest preference.
  A setting change does not interrupt an active build or replace its pinned mode.
  Legacy `recommendation.strategy = "deejai"` supplies the default when no valid
  saved mode exists.
- **Reproducibility:** changed mode/ranking inputs change generation identity.
  Enhanced generation records `multichannel/v18+iterative/v1`; the desktop
  engine-only wrapper uses `deejai/v4+engine-only/v1`. The original `deejai/v4`
  evaluation baseline remains available.
- **Caches:** older hostless cache rows and permanent identity projections are
  not reused because their origin or matching policy cannot be established.
  This can cause a one-time metadata refresh, not deletion of playlist history.
- **Privacy:** prompt inference, history and taste data remain local. Online
  discovery sends extracted genre/reference queries to providers; AcousticBrainz
  receives resolved recording IDs and Deezer receives track lookups. Setup
  downloads models/data, and Soundiiz receives playlist details during export.
  The app is local-first, not entirely network-free.
- **Audio:** preview audio is discarded. Derived embeddings, feature comparisons
  and saved evidence can remain locally reusable until explicitly cleared.
- **Developer dependencies:** helper-only Python ONNX, Torch and Transformers
  dependencies were updated. This does not add Python to desktop packages,
  change the default LLM or mean every export/reference fixture was rerun under
  the newer helper dependency versions.

### Application update behavior

Production builds can check the latest stable GitHub release at startup and
offer a dismissible verified download. Asset name, architecture, size, SHA-256,
approved download location and archive contents are checked before handoff.
A failed update check does not prevent normal startup.

Writable portable/AppImage installations use staged replacement with backups;
Windows NSIS updates request UAC approval; macOS replaces the complete bundle.
OS-managed Linux packages and protected installation folders receive guidance
instead of forced replacement. User data is outside replacement targets.

These checks do not promise transactional rollback of every installer change.
GitHub HTTPS and asset digests are the download trust boundary, not independent
publisher signatures. Save unsaved playlists before accepting a restart.

## 10. Reproduction and supporting evidence

Run the dependency-light suite with `go test ./...`, or the full gate with
`bash scripts/test.sh` on Linux/macOS and `.\scripts\test.ps1` on Windows.

The forty-prompt runner supports `-mode acousticbrainz_first|clap_first|deejai_only`,
`-server-url` for an existing local model server, and `-replay-parsed` with
`-replay` to reuse raw interpretations. Enhanced checks require the installed
catalog, optional metadata/analysis assets and authorized provider access.
A nonzero exit preserves failed observations rather than discarding the report.
