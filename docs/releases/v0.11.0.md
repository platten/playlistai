# Playlist AI v0.11.0 — Better filtering, clearer playlists, and useful logs

Playlist AI 0.11.0 improves how recommendation candidates are checked, makes
playlist outcomes easier to understand, and adds practical debug controls and
frontend regression testing. These notes cover changes since v0.10.0.

## Recommendation shortlists before musical analysis

Evidence-aware recommendation generation now prepares a bounded shortlist aimed
at twice the requested playlist size before checking candidates with
AcousticBrainz and CLAP. For example, a 10-track recommendation request starts
with a target of 20 candidates, then selects eligible tracks toward the requested
10. Required tracks count toward the total rather than being added on top.

- Candidates are ranked and diversity-aware shortlist selection happens before
  expensive audio analysis. Request-local retrieval budgets expand when needed,
  within the configured candidate cap.
- Analysis stops once final selection and sequencing can satisfy the request.
  Rejected or insufficient candidates trigger bounded refill rather than one
  unbounded scan or a repeated request for each track.
- Required tracks, recording deduplication, hard exclusions, artist diversity,
  and ordered journeys remain enforced. Enough accepted tracks alone is not a
  reason to stop if a later journey stage is still missing.
- Refill retains the original request anchor. Provisional alternatives are not
  treated as accepted listening history; accepted selections can inform later
  continuation requests.
- AcousticBrainz-first and CLAP-first preserve their separate evidence policies.
  Deej-AI-only still skips this musical-analysis stage. Direct metadata discovery
  retains its existing oversampling policy; the two-times shortlist applies to
  recommendation candidates, including recommendation fallback.

The strategy identity is now **multichannel/v19**. Regeneration can produce
different playlists; saved playlists keep their existing results and version
information. This release does not promise a full playlist when eligible tracks
or musical evidence are insufficient, and does not claim a measured latency or
musical-quality improvement from the shortlist change.

## Accurate playlist messages

A full-length playlist no longer always displays “A verified partial playlist
was generated.” Track count and musical fulfillment are separate:

| Result | User-facing message |
| --- | --- |
| 10 tracks returned, with some unverified request details | “Playlist created with 10 tracks,” with relevant explanations retained |
| 6 tracks returned for a 10-track request | “Created 6 of 10 requested tracks” |
| Request fulfilled | No partial-result banner |
| Unsupported or ambiguous request | An inability-to-verify or clarification message |

Unknown musical evidence is not relabeled as verified merely because the count
was reached. Older saved-result notices are corrected for display without
rewriting history or promoting their stored outcome. Warnings remain dismissible.

## Log levels and diagnostic privacy

Open **Settings → Application logs → Open logs** and choose the minimum level:
**DEBUG**, **INFO**, **WARN**, or **ERROR**.

- DEBUG enables detailed recommendation diagnostics, including available prompt,
  interpretation, provider, AcousticBrainz, CLAP, and selection evidence.
- Selecting a higher level stops debug collection and clears retained DEBUG
  entries. Filtering the viewer does not discard ordinary retained logs.
- Local dropdown changes invalidate older log polls; changes made in Settings
  appear on the next successful refresh. Consent is checked again before appending a
  diagnostic, including when it changes during payload serialization.
- Verbose in-memory diagnostics do not require lowering the ordinary console log
  level. Retained logs remain bounded and are not written to a persistent log file
  by this feature.

Detailed diagnostics can contain private prompts and listening information.
Review them before sharing. The preference can persist, but log contents are
memory-only. Clearing diagnostic logs does not clear separately stored history or
derived musical analysis. Preview audio cleanup and existing opt-in behavior remain.

## A clearer, more accessible desktop interface

- The theme control uses a **computer** for System, **sun** for Light, and
  **moon** for Dark. It retains an accessible name, keyboard operation, and local
  preference persistence.
- The Generate screen places the description and primary action first, with
  clearer mode guidance and example cards below. Selecting an example fills the
  description and focuses it; generation remains an explicit action.
- Shared theme tokens improve surfaces, hover states, and secondary-text contrast
  in light and dark appearances.
- Track details use a keyboard-accessible button with an expanded state; preview
  controls remain separate. Long names and explanations are better accommodated
  in narrow desktop windows.

## Linux package architecture correction

Linux packaging tasks now explicitly propagate the target architecture to nfpm
for DEB, RPM, and Arch packages. This prevents ARM64 packages from inheriting an
amd64 header despite containing an ARM64 executable. Nine regression cases cover
native, amd64, and arm64 targets across the three formats. Unlike the packaging
repair documented for v0.10.0, the correction is included in this release's source.

## Tests and coverage: progress, not a 95% claim

The contributor gate now includes **35 Vitest/Testing Library frontend tests**,
alongside TypeScript checking and the production build. New backend regressions
cover recommendation pools and refill, required journeys, resolver caching and
ambiguity, intent normalization, semantic evidence, lossless seeds, and logging
privacy. Rendered-browser checks cover log interactions, theme cycling, playlist
outcome messages, and related generation navigation.

Measured on Linux for the application changes included in this release:

| Coverage metric | Result |
| --- | --- |
| Backend statements across `internal/...` | **78.52%**, up from 76.89% |
| Core domain statements | **98.3%** |
| Logging statements | **97.9%** |
| Resolution statements | **100%** |
| Frontend lines | **6.81%** |
| Frontend statements / branches / functions | **6.43% / 4.96% / 5.03%** |

**The requested repository-wide 95% target is not achieved.** The new separate
coverage command correctly fails below that target; ordinary passing CI is not
a coverage guarantee. Backend coverage excludes root bootstrap and command-line
and packaging tools; frontend measurement includes all application TS/TSX modules,
including unimported screens, and excludes only declarations and tests. Native
build variants require their own host measurements. Browser checks are separate
evidence and are not counted in the Vitest percentages.

Reproduce the standard gate and separate coverage check:

```sh
bash scripts/test.sh
bash scripts/coverage.sh
```

```powershell
.\scripts\test.ps1
.\scripts\coverage.ps1
```

The application tree passed the full local Linux gate: shell regressions, bindings
generation, 35 frontend tests, typecheck, production build, Go vet, pure-Go core
compilation, race-enabled Go tests, and lint with zero issues. Earlier rendered UI
checks passed; existing Settings fixture console warnings remain documented and
are not interpreted as coverage. Windows coverage-script execution was not
verified locally. No new held-out listening study, forty-prompt comparison, or
end-to-end performance benchmark was performed for this release.

## Upgrade, packages, and limitations

No user-data reset or intent/history migration is required. Existing settings,
catalogs, metadata, profiles, and installed models remain compatible. Neither the
default language model nor the analysis-model recommendation changes in 0.11.0.
Model weights and large datasets remain separate wizard downloads; the desktop
application does not acquire a Python dependency.

Packages are built for Windows x64/ARM64 (NSIS and portable ZIP), Linux x64/ARM64
(AppImage, DEB, RPM, Arch package, and portable TAR.GZ), and Apple Silicon macOS
(DMG and application ZIP). The workflow also generates a winget manifest ZIP.
There is no Intel Mac package. Signing and notarization depend on configured
credentials, so operating-system trust prompts may appear.

Musical analysis still depends on available metadata and preview coverage.
CLAP similarities are not probabilities, and this release does not establish
general-fit calibration or properties of unheard portions of tracks. Unsupported
criteria and insufficient evidence remain visible instead of being concealed
by arbitrary full-length results.

## Release artifact verification

The [release packaging workflow](https://github.com/platten/playlistai/actions/runs/34555088628)
and [hosted CI](https://github.com/platten/playlistai/actions/runs/34555111265)
passed every job, including the Windows contributor gate and both Windows
installer architectures. All **16 application packages plus the winget ZIP** matched the
approved filenames, nonzero sizes, and GitHub SHA-256 digests. Both installer
hashes in the winget manifest match their corresponding Windows assets.

The downloaded Linux x64 binary and Windows x64 binary (executed on Windows
through WSL interoperability) report **0.11.0** and pass `--check-audio-worker`.
This probe confirms compiled worker availability, not model inference. Linux
x64/ARM64 executable architectures and DEB metadata were inspected; the ARM64
Arch package declares `aarch64`. The macOS ZIP passed its integrity check and
contains 0.11.0 bundle metadata. Native macOS and Windows ARM64 execution, RPM
header inspection, signing/notarization, and complete installed-updater flows
were not independently exercised in these local artifact checks.
