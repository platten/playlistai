# Playlist AI v0.11.1 — Verified genres and a more reliable generation lifecycle

Playlist AI 0.11.1 tightens single-genre recommendations, stops unnecessary track
analysis, and fixes state, storage, and lifecycle errors. It also publishes a
new, deliberately limited benchmark replay—including failures rather than only
successful playlists. These notes cover changes since v0.11.0.

## Every track must fit a single requested genre

When you specify one playlist-wide genre, every recommended track must have
affirmative evidence for that genre. The check runs before selection and again
on the assembled playlist, including required tracks.

- Best-available mode, discovery, diversity, and listening history cannot bypass
  genre eligibility. Unknown evidence is no longer permission to fill the list.
- Established aliases and directional subgenre relationships remain supported:
  techno can satisfy electronic, but electronic alone does not prove techno.
  Influence and fusion are not automatically treated as equivalent genres.
- Evidence can come from provenanced musical metadata, resolved track tags, a
  compatible grounded-description index with complete query coverage, or a
  supported calibrated audio assessment. Catalog identity, artist/title words,
  and uncalibrated preview similarity do not establish genre.
- Sparse sidecars no longer hide valid metadata fallback. Compatible semantic
  evidence can also verify candidates outside an index's retrieval shortlist.
- If too few tracks qualify, the app returns fewer tracks with an explanation.
  Required tracks that conflict with genre eligibility request clarification.
  A request can return no tracks when there is no defensible evidence.

**Deej-AI-only does not verify genres.** A single-genre request in that mode now
returns an unsupported outcome suggesting AcousticBrainz-first or CLAP-first,
instead of an unchecked playlist. Artist-based engine-only recommendations remain
available. Deliberate multi-genre requests and category journeys retain their
existing semantics; soft mood and texture preferences are not all promoted to
hard genre filters.

See [single-genre verification](https://github.com/platten/playlistai/blob/v0.11.1/docs/single-genre-verification.md)
for evidence rules and compatibility details.

## Stop work when a valid playlist is ready

Recommendation generation still prepares a bounded shortlist targeting twice
the requested count, but no longer analyzes surplus candidates once selection
and sequencing can produce the requested playlist. Required tracks count toward
the total. Rejected candidates and incomplete journeys still permit bounded
refill; the stop condition is a valid playlist, not merely enough candidates.

Related corrections include:

- Refill excludes already-attempted semantic candidates before top-K selection,
  avoiding repeated pages that cannot improve the result.
- A failed later retrieval preserves an already usable candidate pool and reports
  the interruption. An exhausted audio-session budget preserves accepted tracks;
  cancellation of the parent request remains cancellation.
- Required waypoints respect hard artist spacing, including scarce separators
  between same-artist waypoints, or report a conflict.
- Iterative completion and final output share one assembly operation, reducing
  duplicated ranking, selection, and sequencing logic.

## Saved playlists, navigation, and feedback

- Loading a saved playlist cannot submit the previously selected record while a
  slower load is pending. Late responses cannot replace the newer selection.
- Editing a saved description creates a fresh request. An unchanged saved result
  can be displayed without rebuilding or inventing a new generation identity.
- Navigating between screens retains the active result, accepted controls,
  generation seed, and export draft.
- Exposure is recorded only when the UI acknowledges displaying a result.
  Discarded builds and repeated acknowledgments do not add exposure, and exposure
  is never treated as a like.
- Clearing taste data invalidates pending profile writes and display tokens, so
  in-flight work cannot restore the cleared information.
- Historical playlist messages use the domain outcome. Reaching the requested
  count does not retroactively verify an old playlist's musical requirements.
- Generate no longer shows redundant **Edit description** buttons; its description
  remains directly editable.

## Safer settings, storage, and runtime management

Settings now use atomic replacement and acknowledge successful persistence.
Corrupt preferences are preserved with an actionable mutation error rather than
silently overwritten. A custom `data_dir` rebases implicit catalog/cache paths
while retaining explicitly configured paths; existing files are not relocated.

SQLite stores share escaped URI construction, preventing reserved path characters
from redirecting access. If startup detects a recognizable database at a legacy
misinterpreted path, it warns rather than silently creating an empty replacement.
Recovery is intentionally not automatic: close the app and back up the database
and any `-wal`/`-shm` files before reviewing a recovery destination.

Other fixes validate catalog embedding headers, honor cancellation while hashing
downloads, prevent slow model activation from undoing a newer selection or clear,
and publish complete catalog service snapshots with explicit shutdown ownership.
Intent normalization no longer mutates caller-owned vocal preferences, and
validation rejects nonfinite resolution weights. Refactoring separates intent
normalization, migration, validation, capability checks, and lifecycle ownership
without replacing the recommendation engine.

## Measured performance—not a universal speedup claim

On the Linux/WSL2 development host, a production-catalog benchmark using 956,917
tracks, a ten-track Boards of Canada request, seed 42, and five samples measured:

| Recommendation-only variant | Median | Range |
| --- | ---: | ---: |
| Uncached exact retrieval | 60.350 ms | 59.344–62.052 ms |
| Request-scoped cache | 62.773 ms | 61.998–64.975 ms |

Both variants produced identical playlists and scoring evidence. The cache was
about 4% slower for this short request and allocated more memory; the website no
longer presents the historical 5.8× result as a current universal improvement.
These timings exclude parsing, providers, audio analysis, and startup.

Separate synthetic measurements found the 100-track category-journey fixture
improved from 72.697–73.754 ms to 23.039–23.748 ms, with allocation volume reduced
from 58.784 MB to 1.274 MB per operation. This is a sequencing microbenchmark,
not whole-app latency or evidence of better music. Hosts were not dedicated
benchmark machines, and results should not be generalized to every request.

Commands, raw timing samples, hardware, and limitations are recorded in the
[performance report](https://github.com/platten/playlistai/blob/v0.11.1/docs/performance-and-model-evaluation.md)
and [codebase review](https://github.com/platten/playlistai/blob/v0.11.1/docs/codebase-review.md).

## Forty-prompt replay: incomplete coverage remains visible

The September 11 replay requested ten tracks per prompt and tested a minimum of
five distinct recordings, diversity, and other contract assertions. It reused
saved interpretations and cached derived features; **it was not fresh LLM/CLAP
evaluation or a held-out listening study**.

| Mode | Completed / 40 | Interrupted | Unattempted | Passed all assertions / completed |
| --- | ---: | ---: | ---: | ---: |
| AcousticBrainz-first | 38 | 2 | 0 | 11 / 38 |
| CLAP-first | 27 | 2 | 11 | 7 / 27 |
| Deej-AI-only | 40 | 0 | 0 | 9 / 40 |

In total, 105 of 120 mode/cases completed; four remained interrupted and eleven
were unattempted. For this replay the all-assertions, at-least-five, and
exactly-ten success counts were the same. **The five-track target for every
prompt was not achieved.**

Both enhanced modes returned zero tracks for “Classical, 10 tracks.” and
“Electronic music. Make a 10-song playlist.” with insufficient-genre-evidence
explanations, rather than unrelated filler. Preview evidence was sparse: only
2 of 112 selected AcousticBrainz-first tracks and 2 of 72 CLAP-first tracks had
analyzed preview evidence. Neither mode selected a pick with an available
`acousticbrainz_intent` scoring component. No new preview bytes were downloaded.
Native CLAP worker health passed, but this does not establish fresh inference
quality; the worker used CPU execution, not GPU inference.

No completed result violated the recording-duplicate, adjacent-artist, or
excluded-artist assertions. Some short results failed diversity. This is not an
independent genre-quality assessment and does not establish a winning source
priority; cache warmth, completed case sets, and concurrent work differed.

Known unresolved findings include a CPU-active catalog-resolution scan during
the punk request that did not promptly honor cancellation, ambiguous reference
resolution, and MusicBrainz HTTP 503 responses. Some bounded stages needed forced
termination. These are documented limitations, not fixed-performance claims.
See the [complete replay protocol and results](https://github.com/platten/playlistai/blob/v0.11.1/docs/three-mode-rerun-2026-09-11.md).

## Validation and coverage

The local Linux repository gate passed for the included application changes:
shell checks, generated Wails bindings, **150 frontend tests**, TypeScript
checking, production frontend build, Go vet, pure-Go core compilation,
race-enabled Go tests, and lint with zero issues. Seven rendered Chromium
workflows covered generation, recommendations, wizard, logs, export, updates,
and saved-session navigation. The website also passed checks at five viewport
sizes. These local checks do not establish hosted release-build success or
native Windows/macOS execution.

The refactor's recorded inclusive coverage was **83.8749% backend statements**;
frontend coverage was **99.17% lines, 97.29% statements, 97.31% functions, and
91.01% branches**. These measurements precede the final single-genre additions
and are not a new release-tree coverage measurement. The repository-wide 95%
target is **not achieved**; the separate coverage check correctly fails below
the target without excluding application modules.

```sh
bash scripts/test.sh
bash scripts/coverage.sh
```

```powershell

```

See [coverage scope and remaining gaps](https://github.com/platten/playlistai/blob/v0.11.1/docs/test-coverage.md).

## Upgrade and compatibility

- No user-data reset is required. Intent schema remains **version 8**. Existing
  installed models, assets, settings, and history retain their supported formats.
- Normalizing a single positive genre preference now preserves it as an essential
  playlist criterion, including when rebuilding older saved requests. Stored
  playlists are not rewritten or retroactively declared genre-verified.
- The strategy identities are **multichannel/v22** and
  **deejai/v5+engine-only/v2**. New builds may return different or shorter results;
  saved generation versions remain intact. The baseline Deej-AI walk remains
  available for evaluation.
- Neither the default LLM nor the analysis-model recommendation changes to conceal
  missing evidence. Large models and catalogs remain separate wizard downloads.
  Desktop runtime code does not acquire a Python dependency.
- The existing packaging workflow targets Windows x64/ARM64, Linux x64/ARM64,
  and Apple Silicon macOS, plus a winget manifest bundle. There is no Intel Mac
  package. Signing/notarization depend on configured credentials; unsigned
  artifacts may trigger operating-system trust warnings. Native package behavior,
  model inference, and updater installation require their own platform checks.

Musical evidence coverage remains the principal limitation for broad category
requests. CLAP similarities are not probabilities, preview evidence covers only
the analyzed segment, and this release does not promise a full playlist when
essential criteria cannot be established.
